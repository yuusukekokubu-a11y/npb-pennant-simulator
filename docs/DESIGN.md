## 1. 全体構成
<!-- プログラムをどんな部品に分けるか -->

基本方針として、**画面(入出力)** と **シミュレーション本体** を分離する。

```
[画面:ブラウザ]  ←→  [シミュレーション本体]  ←→  [保存の差し替え口]
                                                 ├ ローカルのフォルダ
                                                 ├ 1ファイルの書き出し/読み込み
                                                 └ ブラウザ用の保存
```

- シミュレーション本体は画面に依存せず、単体でテストできるようにする。
- 画面はブラウザの中で動かす(Python をブラウザ上で実行する。D-080、D-081)。サーバーは使わない。
- 計算本体は Python 標準のライブラリだけで作り、ファイルの読み書きを直接書かない。保存は差し替え口を通す(D-083)。
  - 初期データ(`src/pennant/data/*.json`)は、パッケージの中のデータとして読む(`importlib.resources`)。ブラウザでもそのまま読める。

### 2.1 ファイルの大きさと、どこに何を書くか(保守②。D-288、D-291)
- src と web の 1 ファイルは 800 行以内を目安にする。超えたら分けるのを基本にし、分けないときは下の表に理由を書く(tests と scripts は目安の対象外)。
- 画面から呼ぶ関数を足すときは、`src/pennant/api/` の分野の合うファイルの Mixin(機能ごとに分けたクラスの部品)に足す。合うファイルがなければ、ファイルを足して `api/__init__.py` の `Game` の部品の並びと説明の一覧に加える。答え合わせ用の関数は今までどおり `answers.py`。
- 画面の処理は、画面ごとの `web/js/*.js` に書く。2 つ以上の画面で使う部品は `parts.js`、画面の状態の初期値は `core.js` の `state`、裏とのやり取りは `backend.js`。ボタンと処理のつなぎは入口の `app.js`。新しいファイルは `app.js` か使う側から import し、`scripts/build_web.py` は `web/js/` の全部を写す。
- 保存形式を新しくするときは、`save_migrations/` に `vNN_to_vMM.py` を足して `MIGRATIONS` に加え、点検は `save_checks.py`、読み込みの順序は `savegame.py` に書く。

800 行を超えるファイル(src・web。保守②の後):

| ファイル | 行数 | 分けない理由 |
| --- | --- | --- |
| `src/pennant/draft.py` | 1029 | オフの手続きの計算本体。段階の進行・AI の判断・契約の扱いが互いに呼び合っていて、分けると互いを読み込み合う形(循環)になり、関数の置き場所を組み直す必要がある。超過は 29 行で、次の ①b・② は画面側の依頼なので、次に手続きの計算を変える依頼のときに分ける。 |
- 乱数はすべて `random.Random(シード)` から取る。同じシードなら同じ結果になる(D-006)。
- 依存ライブラリは使わない(Python 標準ライブラリのみ)。テストには pytest を使う。

## 3. データ設計

### 3.1 初期データ(テンプレート)
- 架空の球団・選手のみを使う。
- コードに直書きせず、外部ファイルから読み込む。
- ファイル形式・置き場所(D-050 で決定):
  - 形式は JSON(セーブデータと同じ形式にそろえる)。先頭に `format_version`(形式のバージョン番号)を持つ。
  - 既定のファイルは `src/pennant/data/` に置き、プログラムと一緒に配る。別のファイルの場所を渡して差し替えることもできる。
  - 読み込むときに検証し、値の欠け・範囲外・割合の合計の不一致・型の補正の釣り合いの崩れなどを、場所と理由つきでまとめて知らせる。

### 3.2 セーブデータ(D-004〜D-006、D-068、D-100〜D-104)
- **1つのファイル**:拡張子 `.sav`、中身は ZIP(`zipfile` と `BytesIO` でメモリ上で作る。一時ファイルは作らない)。
  | ZIP の中のファイル | 中身 |
  | --- | --- |
  | `manifest.json` | 形式の名前・バージョン番号・保存日時・セーブデータの名前・中のファイルの一覧 |
  | `state.json` | シード、設定値(生成・名前の部品・打席・試合・シーズン)、リーグ(球団・選手。隠し情報と状態を含む)、シーズンの状態(現在の日・ローテーションの位置)、各試合の前の状態・先発を飛ばしたか、遊ぶ人の選択(`user.my_team_id`:自球団。形式の版 2 から) |
  | `logs/season-1.jsonl` | 1行に1試合(試合の結果と打席ログ)。ZIP の圧縮だけで、二重には圧縮しない |
- **乱数**:シーズンは、試合ごとのシードをシーズンのシードから作る(D-088)ので、持ち越す乱数の状態はない。保存するのは初期のシードだけで足りる(日程も、シードと設定値から作り直し、保存した試合と一致するかを確かめる)。
- **保存日時**は manifest にだけ入れ、指紋の元には入れない。ZIP の中の日時は固定する(同じ状態なら、保存日時のほかは同じ中身になる)。
- **保存の差し替え口**(D-101。`storage.py`):`Storage` の形(`write(name, data)`・`read(name)`・`list()`)。
  - `LocalFolderStorage`:PC のフォルダ(既定 `~/.npb-pennant-simulator/`)。
  - `MemoryStorage`:メモリ(テストとブラウザ)。
  - ブラウザのファイル選択・ダウンロード:テスト用ページ(`web/`)が `MemoryStorage` とファイルを受け渡す。
  - 計算本体でファイルを読み書きするのは `storage.py` だけ(設定ファイルの場所を指定して読む機能と、パッケージに同梱した初期データの読み込みも、ここに集めた。D-092)。テストで確かめる。
- **検証**(D-102):読み込みでは、ZIP → manifest → バージョン(古い版は変換)→ 状態の JSON → 設定値(各設定の検証をそのまま使う)→ リーグと選手 → シーズン → 打席ログ、の順に点検し、問題をすべて集めて、場所と理由を日本語で示す。点検が済んでから、新しい状態を作って返す(今の状態には触れない)。
- **旧版の変換**:`MIGRATIONS`(版 n の状態を、版 n+1 の形に直す関数の表)を順に当てる。版 6(F2):`year`(何シーズン目か)、`history`(シーズンごとの集計。打席ログは直近 `log_seasons` シーズンだけ `logs/season-<年>.jsonl`)、`offseasons`(年度ごとの引退・入団・能力の増減)を足す。版 5 は year = 1・履歴なしとして読む。
- **ログから求め直すもの**:成績の元の数(D-096)に加え、打撃・走塁・守備の得点(第3弾②。D-165)も打席ログから再集計する。保存はしない(形式の版は 5 のまま)。
- データが大きくなったら、形式のバージョン番号で見分けて、データベース(SQLite:1つのファイルで動く小さなデータベース)へ移行できるようにする。

## 4. シミュレーションの仕組み

### 4.1 1回の打席の計算(`plate_appearance.py`。D-035〜D-038、D-046)
- 入力:打者、投手、守備側の野手8人(ポジション → 選手。投手と指名打者は含まない)、走者・アウト状況(24通り)、乱数。
- 打者は野手でなければならない(投手は打席に立たない。指名打者制。D-046)。
- **オッズ比法**:リーグ平均の率 p を「オッズ」p/(1−p) に直し、打者側・投手側・左右の相性の倍率を掛け、確率に戻す。
  結果が複数あるので、最後に合計が 1 になるよう割り算で調整(正規化)する。
- **能力から倍率**:倍率 = (10点あたりの倍率) ^ ((能力値 − 50) / 10)。能力 50 で 1 倍。能力ごと・結果ごとに設定できる。
- 使う能力値は「現在の能力 + 好調・不調 × 影響の大きさ」。型・成長タイプ・潜在能力・年齢・名前は使わない(D-043)。
- **第1段階**:三振・四球・死球・本塁打・インプレー。インプレーはリーグ平均の残りで、倍率は掛けない。
- **第2段階**(インプレー):
  1. 打球の種類(ゴロ・ライナー・フライ):打者・投手のゴロ/フライ傾向、打者の打球の質(ライナー)。
  2. 担当ポジション:打球の種類ごとの割合表で決める(打者の左右では変えない)。投手が担当のときは、守備の能力を固定値で使う。
  3. 結果:まず「野手が処理できない打球」(打球の種類ごとの割合。必ず安打)かを決め、処理できる打球は、安打・失策・アウトをオッズ比法で決める。
     - 安打:打者の打球の質・走力(ゴロのみ)、投手の打球抑制(効果は小さい)、担当野手の守備範囲・肩(ゴロのみ)、左右の相性
     - 失策:担当野手の捕球
  4. 安打の内訳(単打・二塁打・三塁打):打球の種類ごとの割合に、打者の長打力(二塁打)・走力(三塁打)の倍率を掛ける。
     - 担当ポジションごとの内訳(`in_play.<打球の種類>.extra_base_by_fielder`)があれば、そちらを使う(D-072)。内野手(投手・捕手・一塁・二塁・三塁・遊撃)はここに書く。投手・捕手・二塁手・遊撃手は単打だけ、一塁手・三塁手は単打と少しの二塁打(長打力で起きやすさが変わる)。
     - 書かれていないポジション(外野手)は、打球の種類ごとの内訳(`extra_base`)を使う。
     - 野手が処理できない打球にも、同じ内訳を使う。
- 記録(`PlateAppearance`):結果、打球の種類、担当ポジション、野手が処理できない打球だったか、打者・投手の ID、実際に立った打席の左右、走者・アウト状況、決着球の球種(予約欄。今は空欄)。
- 計算方法は、`probabilities`(確率)と `resolve`(乱数で決める)を持つクラスなら差し替えられる(`PlateAppearanceModel`)。
  試合の計算からも使うため、`rating`(好調・不調を含む能力値)と `fielding`(担当ポジションの守備の能力)も持つ。

### 4.2 1試合の進行(`game.py` ほか。D-059〜D-062)
- 入力:2チームの編成(`TeamSetup`:一軍29人、スタメンと打順、先発投手)、乱数、打席の計算、設定、監督(采配のルール)。
  疲労は選手の「状態」(`Player.state.fatigue`)から読む。試合は入力の選手を書き換えない(疲労は試合後に `apply_game_fatigue` で足す)。
- 出力(`GameResult`):両チームの得点、イニングごとの得点(行わなかった裏は空)、延長・引き分け・サヨナラの有無、打席ログ全体、投手ごとの登板記録、スタメン。
- **イニングの進め方**:3アウトで攻守交代。9回表のあとホームがリードしていれば終了。9回以降の裏に勝ち越したら、その打席で終了(本塁打以外は、勝ち越しに必要な分だけ得点を数える)。延長は上限まで。
- **サヨナラの得点の打ち切り**:本塁打以外は勝ち越しに必要な分だけ得点を数え、取り消した走者は3塁で止まったものとする。後ろの走者は、前の走者を追い越さない塁で止める(同じ塁に2人いないように)。
- **打席ログ**(`GamePlateAppearance`):イニング・表裏・攻撃チーム・打順・打者・投手・点差・走者とアウト・打席の記録に加え、各走者の動き(`RunnerMove`:どの塁からどの塁へ、アウトか、出塁させた投手、失策で出塁したか、失策が関係した動きか)、得点、併殺・犠牲フライ・サヨナラ。
- **走者の進塁**(`baserunning.py`):固定ルール(押し出し、本塁打・三塁打で全員生還、三振・ライナーアウトは進塁なし)と、確率表 × 能力の倍率(オッズ比法)の組み合わせ。
  - 単打:3塁走者は生還。2塁走者は外野への単打なら生還を判定、内野安打なら3塁まで。1塁走者は外野への単打で3塁が空いていれば3塁を判定。
  - 二塁打:2・3塁走者は生還。1塁走者は生還を判定(しなければ3塁)。
  - ゴロ:2アウト未満で1塁に走者がいれば併殺を判定。併殺でなければ打者アウト、詰まっている走者は進み、詰まっていない2・3塁走者は進塁・生還を判定。
  - フライ:2アウト未満で外野フライなら、3塁走者の生還(犠牲フライ)と2塁走者の3塁進塁を判定。内野フライは進塁なし。
  - 失策:打者は1塁へ、走者は1つ進み、さらに1つ進めるかを判定。
  - 走塁死は入れない(D-059)。
- **投手の起用**(`manager.py`・`fatigue.py`):
  - 先発の打者数の上限 = 基準 + (スタミナ − 50) / 10 × 係数 − 疲労 × 係数(下限あり)。イニングの終わりに上限以上なら降板。失点(出塁させた走者の生還)が上限に達したら、その場で降板。
  - 救援は1イニング単位。役割(抑え・中継ぎ(勝ち)・中継ぎ・敗戦処理)を総合値の順で割り当て、場面(イニングと点差)で使う役割を決め、疲労の少ない投手から選ぶ。
  - 救援が使い切られた・疲れているときは、疲労の少ない先発を救援に回す。それでもいなければ、今の投手が続投する(記録 `forced_extra_innings` が残る)。
  - 疲労は投げた打者数 × 係数で増え、1日ごとに 回復量 × 回復力の倍率 だけ減る(`advance_day`)。疲労が上限を超えた投手は登板できない。
- **一軍・スタメン・休養**(`manager.py`):
  - 一軍:先発型6・救援型8、捕手2+捕手以外の7ポジションに1人ずつ+総合値の高い野手6人(計29人)。
  - スタメン:各ポジションで総合値が最も高い野手+指名打者(残りで打撃の高い打者)。
  - 打順:3〜5番は長打の高い3人(4番が最も高い)、1・2番は出塁の高い2人(足の速いほうが1番)、6〜9番は打撃の総合の順。
  - 休養:主力は一定の確率で休み、控えが同じ打順・ポジションに入る。同じポジションの控えがいなければ近いポジションの控え(守備の能力を少し下げる)、それもいなければ誰か(大きく下げる)。捕手の控えがいなければ休ませない。守備適性そのものは F3 で扱う。
- **差し替え**:采配は `Manager` の形(一軍の選抜・スタメン・先発・降板の上限・救援の選び方)を持つクラスなら入れ替えられる。既定は `SimpleManager`。

### 4.3 シーズン(実装④。D-066、D-087)
- **日程**:ラウンド制。各リーグ6球団を、総当たり1巡(5日)ずつの組み合わせで並べ、25巡して125試合(試合数は設定値)。2つのリーグは同じ日に並行して行う。
- **ホームとアウェイ**(D-087):同じ相手との対戦ごとに交互。各ペアの25試合のうち13試合のホーム権を持つ側を、各チームが2〜3組で持つよう、シーズンのシードで割り振る(ホームは各チーム62か63試合)。
- 日程を作る部分は差し替えられる形にする(休養日・3連戦・交流戦は、別の日程の作り方を足して入れる)。
- **1日の流れ**(D-087):スタメンと先発を決める → 試合 → 疲労を加える(`apply_game_fatigue`)→ 結果を順位表に反映 → 1日を進めて回復させる(`advance_day`)。先発は6人ローテーションで、疲労が大きい投手は飛ばす。
- **シーズンの結果**:最終順位表、全試合の結果、全打席のログ。優勝は各リーグの最高勝率。ポストシーズンは後から足せる形にする。
- **サヨナラの打ち切りの記録**:得点を打ち切った打席に印を付ける(`GamePlateAppearance` に項目を足す)。
- **順位**:勝率(引き分けは分母に入れない)→ 勝利数 → 直接対決の成績。同順位を許す設定も持つ。
- **乱数**:試合ごとのシードを、シーズンのシードと試合の通し番号から、SHA-256(`hashlib`)で決める(`derive_seed`。組み込みの `hash()` は使わない。D-088)。日程の割り振りも、シーズンのシードから同じ方法で作った乱数で決める。
- **1試合の再現**:各試合の前の状態(両チームのローテーションの位置と、一軍の投手の疲労)を `GameContext` として残し、`Season.replay_game(番号)` で、その試合だけをもう一度計算できる(シーズンの状態は変えない)。
- **進め方の関数**(画面から呼ぶ):`play_day()`(1日)、`play_days(n, progress)`(n日)、`play_to_end(progress)`(最後まで)。`progress` には、1日ごとに(終わった日数, 全日数, 終わった試合数, 全試合数)を知らせる。
- **日程の差し替え**:日程は `ScheduleMaker` の形(`make(league, rng) → Schedule`)を持つクラスなら入れ替えられる。既定は `RoundRobinSchedule`(円の方式で1巡5日を作り、巡ごとに日の並びを入れ替えて25巡)。休養日・3連戦・交流戦は、別の作り方として足す。
- **ホームの多い組の割り振り**:チームを乱数で円に並べ、円の上で1つ先・2つ先の相手に対しては自分が13試合のホームを持ち、ちょうど半周先の相手とは円の前半のチームが持つ(6チームなら各チーム2組か3組)。
- **順位の決め方**:勝率 → 勝利数 → 直接対決の勝率(同じ成績どうしの対戦だけで計算)→ 抽選(シーズンのシードから決まる順)。同順位を許す設定(`standings.allow_shared_rank`)では、勝率が同じチームを同じ順位にする(表の並びは上の順)。ゲーム差は、首位との差と、1つ上の順位との差の両方を持つ。
- **ポストシーズン**:`SeasonResult`(最終順位表・優勝・全試合)を受け取る別の処理として、後から足す。
- 怪我・成長は入れない(F2・F3)。一軍29人は固定(D-074)。
- **ホームの有利**(D-073):ホームチームの打者の打席で、打席の計算にオッズ比法の倍率を足す。
  - 実装④で校正した値:四球・本塁打・インプレーの安打に 1.06 倍、三振に 0.94 倍(1.0 にすれば有利なし。9章)。最初の案(1.03 倍・0.97 倍)では、ホームの勝率が約51.6%で目標に届かなかった。
  - 結果:20シーズンの平均で、ホームの勝率は約52.8%(目標 52〜54%)。
  - 入れ方:`OddsRatioModel` の第1段階(三振・四球・本塁打)とインプレーの安打の倍率に、ホームの打者のときだけ掛ける。`game.py` が、裏の攻撃(ホームの打者)のときに `home=True` を渡す。
  - 全球団に同じだけ効くので、球場補正の推定(リーグ平均を1.0に合わせる)では打ち消されるはず。球場補正を作る第2弾のテストで確かめる(D-093)。

### 4.4 指標の集計(実装⑤。D-067、D-094〜D-098)
- **ログから計算する**(D-096):成績は、試合の結果(`GameResult` の打席ログと投手の登板記録)から、その都度計算する。成績を別に数え上げて持たない。集計の単位(月別・左右別など)は、ログを作り直さずに後から足せる。
- **部品**:
  - `records.py`:元の数(すべて整数)。1試合ごとの成績(`game_records`)を作り、シーズン通算はその合計(`season_records`)。打者・投手・チームの3種類。
  - `decisions.py`:1試合の勝利・敗戦・セーブ・ホールドの判定(D-094)。
  - `metrics.py`:指標の定義データ(`data/metrics.json`)の読み込み・検証と、計算式による指標の計算・表示の形。
  - `stats_report.py`:確認用の集計(規定到達者の上位、整合チェック、真の能力と成績の関係)。
- **自責点**(簡易版。D-095):半イニングごとに走者を追いかけ、出塁が失策によるもの(`reached_on_error`)か、それまでの進塁に失策が関わった(`advanced_on_error`)走者が生還したら、自責点にしない。それ以外は、その走者を出塁させた投手(`responsible_pitcher_id`)の自責点にする。
- **打点**(D-095):その打席で生還した走者の数。併殺打の打席は0。失策が関係した動き(`advanced_on_error`)で生還した走者は数えない。
- **勝利・敗戦・セーブ・ホールド**(D-094):打席ログで点差を追いかけて判定する。
  - 「勝ち越しの得点」は、勝ったチームが最後にリードを奪った打席の得点。その打席で、勝ち越しに必要な分の生還(走者の動きの並びで前から数える)の走者を、決勝点の走者とする。
  - 勝利投手:その時点で勝ったチームの投手として試合にいた投手(先発は試合の初めから、救援は最初に対戦した打席から試合にいるとみなす)。それが先発で、投球回が5回(15アウト)に満たなければ、勝ったチームの最初の救援投手。
  - 敗戦投手:決勝点の走者を出塁させた投手(`responsible_pitcher_id`)。
  - セーブ・ホールド:登板した最初の打席の前の点差・走者・アウトで、登板時の状況を判定する。
- **指標**(D-097):定義データの計算式(例:`(H + BB + HBP) / (AB + BB + HBP + SF)`)を、標準ライブラリの `ast` で読み、分数(`fractions.Fraction`)で計算する(小数の誤差を出さない)。分母が 0 なら「値なし」(`None`)。式の中で、ほかの指標(例:`obp + slg`)も使える。
- **規定**(D-096):規定打席 =(チーム試合数 × 31 + 5)÷ 10 の整数部分(× 3.1 の四捨五入)。規定投球回 = チーム試合数 × 3 アウト。
- **担当した野手の選手 ID**:打席ログ(`GamePlateAppearance.fielder_id`)に残す(第3弾の守備の計算用)。

- `savegame.py`:`save_game(season, name, saved_at) → bytes`(.sav の中身)、`load_game(data) → Season`(検証してから作る)、`default_file_name(日付)`。
- `newgame.py`:`new_league(seed, 球団名の一覧)`(空欄は架空の初期名)、`validate_team_names`(空白だけ・24文字を超える・制御文字・重複を、理由つきで拒否)、`public_player`(画面用の選手情報。隠し情報と真の能力値を含めない)。

### 4.6 第2弾・第3弾の指標(D-063、D-064、D-070)
- **基準値**(`baselines.py`。D-121〜D-127):打席ログから、整数の集計(状況ごとの得点と回数、結果ごとの状況の移り変わりの回数と得点)を試合ごとに作って足していき、そこから分数で RE24・線形加重・wOBA の重みと目盛り・リーグ平均・FIP 定数を求める。試合ごとに足せるので、シーズン中も、進めた試合の分だけ計算すればよい。
  - 試運転(`trial_baselines`):リーグを複製し、リーグのシードから決めた試運転のシードで1シーズン回して基準値を求める。進み具合を呼び出し側に知らせられる。
  - 既定値と設定:`data/baselines.json`(混ぜ方の定数、FIP の係数の出どころ、既定の基準値)。
  - セーブデータ(形式の版 3):出発点の基準値(出どころ・RE24・線形加重・値)を保存する。版 2 以前は、既定値で読む。
  - 指標の式(`metrics.json`)は、元の数・前に定義した指標に加えて、基準値の名前(`baseline_names` に書いたもの)を使える。基準値がないときは「値なし」。
- **RE24**:打席ログの走者・アウト状況ごとに、イニング終了までの得点を平均して作る。サヨナラで打ち切られた半イニングは、RE24 と線形加重の集計から外す(D-123)。
- **線形加重**:結果の種類ごとに「打席後の得点期待値 − 打席前の得点期待値 + その打席の得点」を平均する。wOBA の重みは、アウトの価値との差を取り、目盛りをリーグの出塁率に合わせる倍率を掛けて作る。
- **FIP**:係数は標準値(本塁打13・四死球3・三振2)。係数を得点価値から導く方式へ切り替えられるよう、係数を設定値として持つ。
- **ホームの有利との関係**(D-093):球場補正の推定で、ホームの有利が打ち消されることをテストで確かめる。
- **重みの混ぜ方**(D-091、D-126):使う値 = 比重 × 今シーズンの値 +(1 − 比重)× 出発点の値。比重 = 累積打席数 ÷(累積打席数 + 定数)、定数の既定は 20,000 打席(設定値)。出発点は前シーズンの最終値(初年度は試運転の値。D-121)。wOBA の重み・目盛り・リーグ平均・FIP 定数・球場補正の推定に共通で使う。
- **指標を足す3つの段階**(D-128):A 定義データだけ(元の数・基準値の組み合わせ)/ B 元の数を足す(`records.py`)/ C 打席ログに情報を足す(指紋が変わる。過去のデータでは「値なし」と表示)。
- **球場の倍率**(②a。D-136〜D-138。`parks.py`、`models.ParkFactors`):真の倍率(本塁打・BABIP。整数の千分率)は球団(`Team.park`)に持つ。リーグのシードから SHA-256 で導いたシードの `random.Random` で、リーグごとに6つを範囲内で一様に引き、合計が 6000 になるよう差を均等に配る。範囲に収まらなければ引き直す(同じシードなら同じ倍率)。打席の計算(`OddsRatioModel`)は `park` を引数で受け取る(省略時は 1.0)。`simulate_game`・`Season._play`・`play_games` が、ホームチームの本拠地の倍率を渡す。
  - 公開用(`Game.stadium`):球場名、本拠地のチーム、本拠地での実際の結果。答え合わせ用(`answers.stadium_answers`):真の倍率。
  - セーブデータ(版 4):`league.teams[].park` に保存。版3以前は 1000/1000(= 1.0)として読む。版 5 で `park_history`(球場 × シーズンの集計)を足した。版4以前は履歴なし(球場補正 1.0)として読む。
  - 指紋:(a) は変わらない(倍率の乱数は別)。(b)〜(h) は倍率を試合に入れたので変わる。(i) 球場の倍率を足す。倍率をすべて 1.0 にしたときの (b)〜(h) を、以前の値(`tests/data/fingerprints-parks-off.json`)と比べるテストで、回帰を確かめる。
- **球場補正の推定**(②b・②c。D-140〜D-150。`parkfactors.py`):球場 × シーズンの整数の集計(`ParkTally`:本拠地とアウェイの PA・HR・BIP・HIT・R)を試合ごとに足していく。推定(`estimate_parks`)は、履歴を合算 → 生の比 → 本塁打と BABIP を縮める(比重 = 本拠地の打席数 ÷(打席数 + 定数))→ リーグの平均で割ってそろえる → 得点の補正を本塁打と BABIP の推定から換算(`parks.run_factor`:推定値を千分率の `ParkFactors` にして打席の結果の確率を求め、wOBA の重みで「1打席あたりの得点の出やすさ」に直す。真の値側 `expected_run_factors` と同じ関数)→ 千分率に丸め、リーグの平均で割ってそろえる(D-147)。縮める計算は分数、換算は小数(打席モデルが小数のため)で、結果を千分率の整数に丸めてから分数に戻す(指紋 (j) のため)。設定は `data/park_factors.json`(本塁打と BABIP の想定する球場差と定数。D-148)。
  - 今シーズンに使う球場補正は、`GameState.park_history`(前のシーズンまでの集計)から求め、シーズン中は変えない。1シーズン目は 1.0。選手ごとの値は、`_StatsCache.player_park_pa`(選手 × 球場の打席数)で重みづけした平均を、指標の式の `pf` に入れる。
  - `run_seasons`:同じリーグを複数シーズン繰り返して回す確認用(F2 の最小の形。加齢などは含めない)。指紋 (j) は、固定のシードで3シーズン回した推定値。
  - 真の倍率は答え合わせ用に残す。
- **守備(第3弾)**:担当ポジションごとに、打球の種類ごとのリーグ平均のアウト率と比べ、アウトにした数の差を得点に換算する。
- **打撃・走塁・守備の得点**(第3弾②。D-160〜D-166。`runvalues.py`):試合の結果(打席ログ)と基準値(`Baselines`:RE24・線形加重・wOBA の重み)から、選手 × シーズンの `PlayerRuns`(打撃・走塁・守備の得点、ポジションごとの守備の得点・機会・守備アウト数)を分数で求める。手順:①今シーズンの記録から「同じ状況」(結果 × 前の状況 × 外野か)ごとの期待値の変化の平均と、ポジション × 打球の種類ごとのアウト率を集計(`SeasonContext`)→ ②打席ごとに、走塁の差を選択の余地があった走者に等分、守備の差(アウトか − 期待のアウト率)× アウトの価値を担当野手に加算 → ③打撃は選手の元の数から wRAA(球場補正つき)。守備アウト数は打順表の守備位置 × 守備側のアウト数。画面には出さない(③で出す)。実測(リーグ 1、10シーズン。`scripts/inspect_run_values.py`):守備の得点と真の能力(守備範囲・肩・捕球の平均)の相関は 1シーズン 0.62、3シーズン 0.62、10シーズン 0.74。1シーズンの守備の得点の標準偏差は 7.9 点(遊撃 11.1、三塁 8.5、捕手 2.0。捕手は担当する打球が少ない)。走塁の得点と真の能力(走力・走塁判断)の相関は 1シーズン 0.55、10シーズン 0.68(走塁判断だけでは 0.27。走力の効きが大きい)。打撃の得点と wRC+ の相関 0.997。`run_seasons` は結果を受け取る呼び出し口を持ち、指紋 (k) と `scripts/inspect_run_values.py` が使う。
- **WAR**:打撃・走塁(進塁の価値)・守備・ポジション補正・控え水準・1勝あたりの得点を組み合わせる。投手は FIP 版と失点版の両方。
- **WAR の計算**(第3弾③a。D-167〜D-173。`war.py`・`data/war.json`):`season_war(results, baselines, runs, records, settings, ...)` が選手 × シーズンの `WarLine`(打者:打撃・走塁・守備・ポジション補正・控え水準・WAR。投手:FIP 版と失点版の得点・守備の調整・球場補正・控え水準・2つの WAR)を分数で返す。1勝あたりの得点は基準値の `lg_r_pa` × 今シーズンの1チーム1試合あたりの打席数 × 4 ÷ 指数。守備位置ごとの按分は `PlayerRuns.outs_by_position`、指名打者は打順表の守備位置が DH の試合の打席数。投手の球場補正は、投げた球場(ホームチームの ID)ごとの対戦打者数で重みづけた、前のシーズンまでの推定(D-142 と同じ考え方)。先発・救援の投球回は `GameResult.pitchers` の登板記録(役割ごとのアウト数)から。画面用(③b。D-179):`war.war_for_results(results, estimates, baseline_settings, war_settings, baselines)` が打撃・走塁・守備の得点と WAR を一度に求める(スクリプトと画面で同じ関数)。`api.Game.war_lines()` は試合数で覚えておき(`_StatsCache` と同じ寿命)、`stats(kind="war")`・`player`・`team` が使う。WAR の表の列は `metrics.json` ではなく `api/common.py` の `WAR_COLUMNS`(指標の式ではないため)。
- 第3弾は①選手生成の変更 → ②打撃・走塁・守備の得点 → ③WAR の順(D-155)。守備の得点は打球ごとの記録(担当野手の ID)から、走塁の得点は進塁の価値から。ポジション補正・控え水準は設定値。投手の WAR は FIP 版と失点版。1勝あたりの得点はリーグの得点環境から(D-156)。
- **ポジション別の型の出現割合**(第3弾①。D-157。`generate.py`・`config.py`):`generation.json` の `position_archetype_shifts` に、守備位置ごとの型の「足す量」(合計 0)を置く。ポジションの割合 = 全体の割合(`batter_archetypes.*.share`)+ 足す量。読み込み時に、各ポジションの合計が 0、各割合が 0〜1、球団の人数(`roster.fielders`)で重みづけした合計が型ごとに ±許容幅(`potential.share_balance_tolerance`)に入ることを検証する(全体の平均が 50 から動かないため)。投手には適用しない。

### 4.7 シーズンの間の処理(F2。D-071、D-180〜D-189)
- `api.Game.year_end()` が、年度の確定 → 加齢 → 能力の更新 → 引退 → 補充 → 次のシーズンの準備、の順で行う(試合の計算とは別の処理の流れ)。
  - 年度の確定:`history.SeasonArchive`(年、順位表、優勝、球団の成績、選手 × シーズンの元の数・球場補正・WAR の内訳、選手の名前・年齢・ポジションの写し、最終の基準値)を作って `GameState.history` に足す。`park_history` に集計を足し(`finish_season`)、基準値の出発点を今シーズンの最終値(混ぜた値)にする。
  - 加齢・能力の更新・引退・補充は `offseason.py`(`run_offseason(league, seed, gen_config, names, settings)` → `OffseasonResult`:引退した選手、入団した新人、能力の増減(隠し情報。答え合わせ用))。乱数は `derive_seed(シーズンのシード, "offseason")`。能力の更新は `aging.current_rating`(揺れは `generation.json` の `variation.ability_drift_sd_per_year`)。引退の確率は `data/offseason.json`(年齢の分 + 能力の分)。補充は `generate.make_rookie(role, position, ...)` を使う関数 `replenish` に分け、F3-1 でドラフトに差し替える。新人の ID は `Y<年>R<番号>`。
  - 次のシーズン:`Season(league, derive_seed(今のシーズンのシード, "next-season"))`。一軍・打順・先発は既存の規則(`SimpleManager`)で組み直す。疲労は 0 に。
- 過去シーズンの成績は `SeasonArchive` の元の数から、その時の基準値と球場補正で指標を出し直す。通算は、元の数から計算できる指標は元の数の合計から、基準値に依存する指標(式に基準値の名前か `pf` を使うもの。`metrics.baseline_dependent`)は各シーズンの値を打席数(投手はアウト数)で加重平均(D-192)。WAR は各シーズンの合計。
- 打席ログは直近 `log_seasons` シーズン(`data/offseason.json`。既定 1)だけ `logs/season-<年>.jsonl` に保存し、それ以前の `SeasonArchive.games` は None(試合のページは開けない)。
- 指紋 (m):固定のシードで年度の確定を 2 回行い、3シーズン目を最後まで回した後の、選手の年齢・能力(千分率の整数)、引退・入団の ID、各シーズンの集計(元の数・WAR)。
- **オフの手続き**(F3-1。D-201〜D-207。`draft.py`):`year_end` は、集計の履歴 → 加齢・能力の更新・引退(`offseason.age_update_retire`)の後、`draft.OffseasonProcedure`(年、シード、指名の順番、巡、候補、市場、指名の履歴、手放した選手、段階)を作って `GameState.procedure` に持つ。観戦のみ(操作する球団なし)なら、その場で `complete` → `finalize`(自動補充 → 市場の残りはリーグを去る → 次のシーズン)。操作する球団があるときは、段階ごとに画面の操作(`offseason_release`・`offseason_pick`・`offseason_pass`・`offseason_next`・`offseason_auto`)で進め、保存は手続きの状態ごと行う。AI の判断(`ai_release`・`ai_choose`)は、球団ごとのスカウト評価(`scouting.quick_overall`:乱数は `derive_seed(手続きのシード, "scout:<球団>:<選手>")`)を使い、差し替え可能な関数にする。候補の ID は `D<年>C<番号>`、自動補充の新人は `Y<年>R<番号>`。事前運転も同じ手続き(全球団 AI)で回す。
- **スカウト評価**(`scouting.py`。D-199、D-212〜D-215):`report(player, team, seed, sd, cuts, margin_z)` → 項目ごとの推定値とふれ幅、総合の推定値とふれ幅、天井の段階、評価方式の版(`method`)、天井の区切り(`cuts`。振り返りで実際の天井を出すため)。`sd` は `{"common": 共通の見誤りの標準偏差, "item": 項目ごとの見誤りの標準偏差}`(球団ごと。既定は設定の段階の値)。乱数(`derive_seed(手続きのシード, "scout:<球団>:<選手>")`)の並びは、①共通の見誤り N(0, common)、②項目ごとの見誤りの平均 N(0, item/√n)、③天井の見誤り N(0, 総合の誤差の標準偏差)、④項目ごとの偏り N(0, item) × n(平均 0 に正規化)。総合の推定値 = 真の総合値 + ① + ②(AI の判断 `quick_value` は ①〜③ だけを引くので速い)。項目の推定値 = 真の値 + ① + ② + ④の偏り。項目の誤差の標準偏差は √(common² + item²)、総合は √(common² + item²/n)、項目間の誤差の相関は common² ÷ (common² + item²)。ふれ幅はそれぞれの標準偏差 × 1.28。天井は潜在能力の総合値 + ③ を、そのオフの候補全体の分位点(`cuts`)で S〜D に分ける。旧方式(版 1。F3-1 の形:総合 N(0, sd/√n)、天井 N(0, sd))は `method=1` として残し、読み込んだ時点で進行中だった手続き(`OffseasonProcedure.method`)だけがそれを使う。入団時の評価は `Player.scouting` に保存する(版 1 の評価はそのまま表示)。
- **ドラフトの振り返り**(D-216。`api.draft_review(team_id, year)` / `answers.draft_review_answers`):入団の経路は `GameState.transactions`(指名・市場・自動補充(`phase="fill"`)・自由契約)から引き、各行に入団時の総合の推定値・ふれ幅・天井を持たせる(引退・退団した選手の行も出せる)。今の所属は選手の有無で判定し、出場と WAR の累計は履歴(`SeasonArchive.war`・`records`)と今シーズンの値を足す。答え合わせ側は、今の真の総合、差、実際の天井(`scouting["cuts"]` があればそれで、なければその年の入団者全体の分位点で判定)、球団ごとの差の平均と標準偏差。事前運転の入団(履歴に残さない)は出ない。
- **選手の一覧の表(自由契約・市場。D-222。`api.roster_table(player_ids, role, kind, sort, order, season)` / `answers.roster_ability_table`)**:個人成績の表(`stats`)と同じ列・値の作り方で、任意の選手の一覧(自球団の全選手、市場の選手)を表にする。基本の列は ポジション・年齢・打席(投手は投球回)で、選んだ種類(基本・セイバー・WAR)の列を続ける。並び順は全部の列(基本の列・成績の全指標・WAR の列。答え合わせ側は能力の項目も)から選べ、表にない指標で並べたときは `extra_column`(名前の隣の固定列)で返す(D-131 と同じ)。成績のない選手(指名されなかった候補)の値は「—」で、並び順によらず最後。手続きの画面は `offseason_table`(公開用)と `offseason_ability_table`(答え合わせ用)で呼ぶ。
- **契約と年俸**(F3-2a。D-230〜D-237。`contracts.py`):選手は `Player.contract`({salary: 年俸(万円)、until: 満了シーズン、history: [{year, salary, years, reason}]})を持つ。`ContractSettings`(`data/contracts.json`)。見込みの WAR `expected_war(age, role, season_wars, scouting, settings)`(`draft.ContractContext.expected` が選手 × 球団ごとに引く):履歴(`SeasonArchive.war` の直近 3 シーズン)があれば、重み(新しい順の設定値)× 出場の係数(打席か投球回 ÷ 設定値。上限 1)の加重平均。なければ、所属球団の評価(`scouting.quick_value` を乱数系列 `contract:<年>:<球団>:<選手>` で引いた総合の推定値と天井)から設定の表(役割ごとの傾きと切片、天井の加点)で求める。30 歳以上は年齢で割り引く。年俸 `salary_for(expected_war, rate)` = 最低年俸 + 単価 × max(0, 見込み)を丸めたもの。契約年数 `contract_years(age, expected_war)` は年齢と見込みで決める(9 章)。単価 `rate_for(expected_list, teams, players, settings)` は毎年のオフに、(基準予算 × 球団数 − 最低年俸 × 選手数)÷ Σ max(0, 見込み) で求め、`GameState.contract_rates`(年 → 単価)に残す。お金のルール `money_rule`(none / loose / standard / strict)と球団ごとの格差 `budget_tiers`(strict のとき、新規開始のシードから `derive_seed(seed, "budget-tiers")` で大 3・中 6・小 3)。予算 `budget_of(team)` = 基準予算 × 格差、上限 = 予算 × 1.10。契約の乱数はすべて別の系列(`contract:…`)で、AI の判断には使わない(D-237)。
- **FA**(F3-2c。D-258〜D-264。`fa.py`):設定は `data/negotiation.json` の `fa`(必要なシーズン数・保持者のしきい値の上げ幅・ラウンド数・AI の倍率と提示数・選手の判定の乱数・初期値の補い方・補償(空))。`Player.fa_seasons` は年度の確定(`api.year_end`)で、そのシーズンの一軍(`Season.actives`。シーズンの最初に決まり、シーズン中は変わらない)の選手に 1 を足す。更改の判定(`negotiation.judge`)は、文脈に `fa_holder` があればしきい値を上げる。`draft.make_offer` は、断った選手が FA 権保持者なら `fa.declare`(球団を離れ、契約は終わり、年数を 0 に戻して `OffseasonProcedure.fa_pool` へ)。手続きの段階 `fa` は自由契約の後。`fa.close_round` が 1 ラウンドを締める:AI の提示を作り(`ai_offers`)、あなたの提示(`fa_offers`)と合わせ、見込みの WAR の高い選手から順に、空き枠と予算を満たす提示の中で満足度が最も高いものを選ぶ(`judge` に提示した球団での出場機会・順位と、`derive_seed(手続きのシード, "fa:<選手>:<球団>:<ラウンド>")` の小さな乱数)。成立したら `set_contract(..., "fa")`、結果は `fa_results`。最後のラウンドの後、残った選手は市場へ。補償は `fa.compensation`(初期は何もしない)の差し替え口。将来の「愛着」の軸は、`negotiation` の軸の種類を足して、提示した球団が元の球団かを文脈に入れれば足せる。
- **予算超過の解消の順**(F3-2b で変更。D-255):`resolve_overrun` は「(年俸 − 最低年俸)÷ 見込みの WAR」の大きい選手から外し、最低人数を守ったままでは解消できなければ最低人数を割っても外す(不足は `finalize` が最低年俸で補充)。あなたの球団は、上限を超えている間は最低人数の選手も外せる(`offseason_release`)。事前運転では志望の判定を行わない(`offseason.PRERUN_NEGOTIATION = "none"`。D-254)。
- **契約更改と志望**(F3-2b。D-243〜D-253。`negotiation.py`):`NegotiationSettings`(`data/negotiation.json`)。軸は設定の `axes`(キー → 名前・理由の文・満足度の種類 `kind`(salary_ratio / depth / standing)・重みの分布の形・軸の強さ・お金のルールが必要か)で、種類ごとの満足度は `satisfaction` が kind で分けるので、軸を足すときは設定を書くだけ(新しい種類のときだけ関数を足す)。選手の志望 `Player.preference`({軸: 重み}。隠し情報)は `draw_preference(選手 ID, リーグのシード, 設定)` が `derive_seed(リーグのシード, "preference:<選手 ID>")` から引く(選手 ID だけで決まるので、付ける時期によらず同じ値。`ensure_preferences` を新規開始・手続きの開始・自動補充・読み込みで呼ぶ)。判定 `judge(設定, 志望, 年数, 年俸, 自動案の年俸, 年齢, 文脈, お金のルール, 乱数)` は 受ける/断る・理由の軸・点数・満足度を返す(点数と満足度は画面に出さない)。出場機会軸の評価は契約と同じ評価(`ContractContext.scout`)で、`depth_ranks` が手続きの最初に数えて交渉の文脈に保存する(保存・再開しても同じ答え)。勝利軸の順位は `OffseasonProcedure.ranks`(年度の確定で公式の順位を入れる。事前運転では空で 0)。乱数は `noise_for` の `derive_seed(手続きのシード, "negotiation:<選手 ID>")` の 1 つだけで、同じ提示には同じ答え。手続きは `OffseasonProcedure.negotiations`(選手 ID → {球団・名前・前の年俸・自動案の年俸・AI の年数・見込み・文脈・状態(pending / accepted / released)・提示の履歴 [{年数・年俸・受けたか・理由}]})を持つ。`draft.apply_contracts_start` が満了者全員の交渉を作り、AI 球団は `ai_negotiate_entry`(D-251)で最後まで進める。あなたの球団は `make_offer`・`release_entry` で 1 人ずつ(`api.offseason_offer` などが入口)、「自動案でまとめて更改」は未提示の全員に自動案。標準以上で算定より高い年俸は `projected_total`(見込みの総年俸)で上限を確かめる。受けた選手は `set_contract(..., "renew", offers=提示回数)`、自由契約は `release_players`(履歴の印 note="negotiation")。終わった手続きの交渉は `Game.last_negotiations` に残す(保存しない。指紋 (p) と集計用)。
- **オフの流れへの組み込み**(D-235):`start_procedure` の直後に `draft.apply_contracts_start`(単価を求め、全球団の満了者を算定で更改。結果は `OffseasonProcedure.renewals`。標準以上なら AI 球団の `resolve_overrun`(AI 球団:見込みの WAR あたりの年俸が高い順に、最低人数を守って自由契約。`proc.budget_releases`)。あなたの球団の超過は、自由契約の段階で手動(`offseason_next` は超過中は拒む。`offseason_auto` は AI と同じ)。ドラフトの指名は巡ごとの年俸(標準以上で上限を超えるならパス。note="budget")、市場の獲得は算定した年俸(上限を超えるなら AI は選ばない、あなたは拒まれる)、自動補充は最低年俸(予算に関わらず)。手放した選手の契約は消える。標準・きびしいでは事前運転も同じ流れ(履歴がないので評価から算定。超過の解消が AI の判断に入る)。なし・ゆるいでは事前運転は契約を扱わず(AI の判断が変わらない。D-237。時間も短い)、新規開始の最後に `initialize_contracts` が全選手の契約を評価から算定して付ける(残り年数は `contract:init-years` の乱数で 1〜契約年数。標準以上は上限に収まるよう最低年俸より上の分を比例で縮める)。
- **オフの手続きの段階と、おまかせ(UI の整理①a。D-271・D-272)**:内部の段階 `PHASES`(renewal・release・fa・draft・market・done)は保存形式のため残し、画面の段階 `STAGES`(contract・fa・draft・market・done)に `stage_of` で対応させる(renewal と release はどちらも「契約」)。`draft.apply_contracts_start` は交渉までにし、AI 球団の予算超過の解消と自由契約は `draft.finish_contract_stage`(契約の段階の終わり。`my_ai` なら自球団の残りの交渉・超過の解消・自由契約も AI と同じ方針)で行う。AI 球団の処理の順序(交渉 → 超過の解消 → 自由契約)は変わらないので、全球団 AI の指紋 (m)〜(q) はこの移動では変わらない。`api.Game.offseason_next` は自分の操作を終えて進む(契約:未決定と上限超過を拒む → `finish_contract_stage(my_ai=False)`。FA:`run_all_rounds(my_ai=False)` で自球団は追加の提示をしない。ドラフト・市場:`_run_turns(my_ai=False)` で自分の番はパス)。`offseason_stage_auto` は今の段階だけを AI の方針で(自球団も)進め、自球団の分の行動の一覧(`auto_log`)を返す。`offseason_auto` は全部(「全部おまかせ」。メニューの中)。契約の画面の表は `api.Game.contract_table(group, kind, sort, order, season, status)`(自球団の今の選手と、この手続きで離れた選手。列は 選んだ指標・ポジション・年齢・今の契約・今回の提示・状態・出場。「全員」は共通の列だけ、ポジションを選ぶと種類の成績の列も)。「自由契約にする」は `offseason_contract_release`(交渉中なら交渉をやめる、契約が残るなら残りの契約を消す)。画面は状態バー(要約・予算・主ボタン)、段階のタブ 5 つ(折り返さない)、説明ブロックなし(D-270)。
- **表の部品(`web/js/parts.js` ほか。D-223)**:個人成績の表の仕組み(見出しの並べ替え、固定列、並べ替えた指標の固定表示、並び順の保持 `sortToggle`)を `statsTable()` に切り出し、個人成績・自由契約・市場・ドラフトの振り返りで共有する。幅に応じた表示は `fluid` の印を付けた表だけに適用する:画面の幅が `WIDE_MIN_WIDTH`(仮置き。9 章)以上なら `<html>` に `wide` の印が付き、`fluid` の表は横スクロールなしで全列を出す(固定列も解除)。既存の表(個人成績・チーム・順位)には付けない(デザインの見直しの第 2 段階で扱う)。固定列の幅と位置(D-267・D-268):名前の列の幅と、その右に固定する指標の列の位置は、CSS の変数 `--table-name-w` の 1 つの値で決め、見出しと本体で同じ値を使う(`box-sizing: border-box` で、余白を含めた幅)。以前は `9em` と書いていたため、文字の大きさが違う見出し(0.8rem)と本体(0.92rem)で幅が 115px と 132px に分かれ、横にずらすと固定列の線が 17px ずれていた。並べ替えた列は、見出しの ▲▼ を別の要素(`.arrow`)にして列の右の余白(`--table-sort-mark-w`)に置き、本体の同じ列にも `sorted` の印を付けて同じ余白にする(▲▼ を除いた見出しの文字の右端と、数値の右端がそろう)。固定列のすぐ右の列は、左の余白を `--table-first-scroll-gap` にする(固定しない広い画面の `fluid` の表では、ほかの列と同じ)。そろいは `scripts/check_table_align.mjs` がブラウザで要素の位置を測って確かめる(幅 360・390・412・768・1280。固定列の線 1px 以内、見出しと数値の右端 2px 以内、余白 8px 以上)。修正後の画面の写し(架空のデータ)は `docs/design/table-align-*.png`。
- 指紋 (n):固定のシードで、観戦のみ(全球団 AI)のオフの手続きを 2 回行った後の、選手(年齢・能力)、入団時の評価、指名・自由契約の履歴。形式 15(2 層の評価。D-212)で (a)〜(m) も変わった(事前運転が評価を使うため。(i) 球場の倍率だけ同じ)。

## 7. テスト方針
- テストには pytest を使う。
- シミュレーション本体は、画面なしで単体テストできるようにする。
- 乱数のシードを固定して、結果を再現できるテストを書く。
- **版をまたいだ再現性**(D-088、D-089):`src/pennant/fingerprint.py` が、決まったシードで (a) リーグの生成、(b) 1試合、(c) 30日分の試合、(d) 1シーズン(実装④で追加)を行い、(e) (d)の集計結果の元の数(実装⑤で追加)、(f) (d)を途中(1・62・125日目)で保存・読み込みして最後まで進めた結果(実装⑥で追加)とあわせて、結果の指紋(SHA-256)を作る。
  - 元にするのは、離散的な結果と、整数・文字列の情報だけ(小数は入れない。入れようとするとエラーにする)。
  - 期待値は `tests/data/fingerprints.json` に固定し、CI の Python 3.10・3.12・3.14 で一致を確かめる。
  - ブラウザのテスト用ページ(`web/`)も、同じ関数で指紋を表示する。
  - 確認用スクリプト:`python scripts/fingerprint.py`
- **GitHub のテストの回し方**(D-279〜D-281、D-285、D-287、D-293、D-294):速いテスト(既定の `pytest`)と重いテスト(`pytest -m slow`)に分ける。PR では、速いテストを 3 つの版で、1 つの版を 3 つのジョブ(指紋の一致の確認・a・b)に分けて同時に回す。計算本体(`scripts/ci_needs_slow.py` の範囲)が変わった PR だけ、重いテストを 3.12 の 3 つのジョブで回す。分け方は `scripts/ci_groups.py`(「残り全部」のジョブがあるので、新しいテストは必ずどこかで回る。抜けと重なりがないことは `tests/test_ci.py` が確かめる)。同じジョブの中では、指紋を `tests/conftest.py` の `current_fingerprints` で 1 回だけ作って使い回す。
- **乱数の使い方の決まり**:乱数は `random.Random(シード)` の中の関数だけを使う。シードは整数か文字列にする(タプルなどは版によって使えない)。集合(set)の並び順に乱数の結果を左右させない(文字列の集合の並び順は、Python を起動するたびに変わるため)。版をまたいで指紋が変わった場合は、その関数を `random()` だけを使った自前の処理に置き換える(D-089)。

## 8. 検討中の論点
<!-- まだ決定ではない。決まったら DECISIONS.md に記録し、上の各節に反映する -->
> ここに書いた内容は**まだ決定ではありません**。壁打ちで検討する候補です。

- **守備適性・兼任、投手の先発・救援の区別**:選手ごとに、主ポジション以外に守れるポジションと得意・不得意を持たせる(第1弾は主ポジション固定。守備適性・兼任は F3 で扱う。D-049)。投手は先発と救援(リリーフ)を区別する。
- **選手の永続 ID・契約情報**:選手に、移籍しても変わらない番号(永続 ID)を付け、契約情報を持たせる(F3 で扱う)。オフシーズンの処理の流れは D-071 で決定した。
- **他球団の判断ロジックを差し替え可能にする**:他球団がどの選手を獲るか等を決める仕組みを、部品として交換できるようにする。
- **投手能力の2層化への備え**:投手の能力を、後から「基礎能力 + 球種ごとの補正」の2層にできる形にしておく。
- **BABIP の検証機能**:同じ設定でシーズンを繰り返しシミュレーションし、BABIP の年ごとの相関(ある年に高い選手が翌年も高いか)を調べる検証機能。
- **年齢カーブの持ち方**:年齢カーブは「潜在能力に対する割合」ではなく、「ピークからの差(点数)」で持つ方向で検討する。20〜80 の目盛りと整合させるため(割合で持つと、目盛りの基準の 50 が動いてしまう)。
- **「奪三振力」の年齢カーブのグループ**:技術系に入れるかパワー系に入れるかは、調整時に見直す。
- **検証の方法**:シーズンを繰り返し回して、リーグ平均の率・得点が一般的な水準に収まるかを確かめ、設定値を校正する。
