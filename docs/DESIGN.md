## 1. 全体構成
<!-- プログラムをどんな部品に分けるか -->

基本方針として、**画面(入出力)** と **シミュレーション本体** を分離する。

```
[画面:CLI → 将来 GUI]  ←→  [シミュレーション本体]  ←→  [データ読み書き]
```

- シミュレーション本体は画面に依存せず、単体でテストできるようにする。
- 画面を CLI から GUI に差し替えても、本体は変更しなくて済むようにする。

## 2. フォルダ・モジュール構成
<!-- モジュール:プログラムを機能ごとに分けたファイルのまとまり -->
計算本体は `src/pennant/` に置く(画面には依存しない。D-009)。

```
src/pennant/
  abilities.py        能力項目・ポジションの名前(数値は持たない)
  config.py           設定ファイルの読み込みと検証(バリデーション)
  models.py           選手・球団・リーグのデータの形(隠し情報は Player.hidden にまとめる)
  aging.py            年齢カーブ(ピークからの差で計算)
  names.py            選手名・球団名・球場名の生成
  generate.py         リーグ全体・新人(ドラフト候補)の生成
  stats.py            分布の集計(開発者向けの確認用)
  data/generation.json  生成に使う数値(仮置き値。9 章)
  data/names.json       名前の部品
scripts/inspect_league.py  分布を表で出す確認用スクリプト(操作画面ではない)
```

- 乱数はすべて `random.Random(シード)` から取る。同じシードなら同じ結果になる(D-006)。
- 依存ライブラリは使わない(Python 標準ライブラリのみ)。テストには pytest を使う。

## 3. データ設計

### 3.1 初期データ(テンプレート)
- 架空の球団・選手のみを使う。
- コードに直書きせず、外部ファイルから読み込む。
- ファイル形式・置き場所(D-050 で決定):
  - 形式は JSON(セーブデータと同じ形式にそろえる)。先頭に `format_version`(形式のバージョン番号)を持つ。
  - 既定のファイルは `src/pennant/data/` に置き、プログラムと一緒に配る。別のファイルの場所を渡して差し替えることもできる。
  - 読み込むときに検証し、値の欠け・範囲外・割合の合計の不一致・型の補正の釣り合いの崩れなどを、場所と理由つきでまとめて知らせる。

### 3.2 セーブデータ
- JSON 形式。
- 保存場所:ユーザーのホームフォルダ内の専用フォルダ(フォルダ名は未定)。リポジトリの外。
- 必ず含める項目:
  - 形式のバージョン番号
  - 乱数のシード
- その他の項目:(未定)
- 読み込み時はバリデーション(データが正しい形かの点検)を行い、壊れていれば分かりやすいエラーを出す。

## 8. 検討中の論点
<!-- まだ決定ではない。決まったら DECISIONS.md に記録し、上の各節に反映する -->
> ここに書いた内容は**まだ決定ではありません**。壁打ちで検討する候補です。

- **走者・アウト状況(24通り)の記録と RE24**:走者の有無(8通り)× アウト数(3通り)= 24通りの状況を打席ごとに記録する。RE24 は、その状況から平均で何点入るかの表(得点期待値)を使い、打席ごとの得点への貢献を測る方法。
- **守備適性・兼任、投手の先発・救援の区別**:選手ごとに、主ポジション以外に守れるポジションと得意・不得意を持たせる(第1弾は主ポジション固定。守備適性・兼任は F3 で扱う。D-049)。投手は先発と救援(リリーフ)を区別する。
- **球場補正(架空の球場)、控え水準の設定値化**:各球団に架空の本拠地球場を設定し、打ちやすさの違いを補正する。WAR の基準となる「控え水準(代わりの選手のレベル)」を設定値(後から変えられる値)として持つ。
- **選手の永続 ID・年齢・契約情報、オフシーズンを独立した処理の流れにする**:選手に、移籍しても変わらない番号(永続 ID)を付ける。年齢と契約情報を持たせる。オフシーズン(シーズン後の期間)の処理を、試合のシミュレーションとは別の処理の流れとして作る。
- **ドラフト候補や FA 選手の「スカウト評価」と「真の能力」のズレ**:プレイヤーに見えるのはスカウトの評価(見積もり)で、本当の能力とは誤差がある、という仕組み。
- **他球団の判断ロジックを差し替え可能にする**:他球団がどの選手を獲るか等を決める仕組みを、部品として交換できるようにする。
- **セーブデータが大きくなった場合の別形式への移行**:複数年分の打席記録などで JSON が大きくなりすぎた場合、SQLite(1つのファイルで動く小さなデータベース)などの形式に移すことを検討する。
- **能力値の内部表現**:能力値は内部では小数で持ち、画面では5刻みに丸めて表示する。内部では 20〜80 の外側の値も許す(極端な選手を表せるようにするため)。
- **スカウト評価の誤差の表し方**:ドラフト候補や FA 選手の「スカウト評価」と「真の能力」のズレを、標準偏差何個分の誤差として表す。
- **決着球の球種欄の予約**:打席ごとの記録に「決着球(打席の結果が決まった1球)の球種」欄を用意しておく。当面は空欄とする(D-025 の将来の球種別分析に備える)。
- **投手能力の2層化への備え**:投手の能力を、後から「基礎能力 + 球種ごとの補正」の2層にできる形にしておく。
- **成績・指標はログから集計**:成績や指標は、打席ごとの記録(ログ)を集計して計算する(成績を別に数え上げて持たない)。
- **古いシーズンのログの扱い**:古いシーズンの打席ログは、集計値への圧縮(まとめた数字だけを残す)か、別形式(SQLite 等)への移行を検討する。
- **BABIP の検証機能**:同じ設定でシーズンを繰り返しシミュレーションし、BABIP の年ごとの相関(ある年に高い選手が翌年も高いか)を調べる検証機能。
- **年齢カーブの持ち方**:年齢カーブは「潜在能力に対する割合」ではなく、「ピークからの差(点数)」で持つ方向で検討する。20〜80 の目盛りと整合させるため(割合で持つと、目盛りの基準の 50 が動いてしまう)。
- **「奪三振力」の年齢カーブのグループ**:技術系に入れるかパワー系に入れるかは、調整時に見直す。
- **オッズ比法の正規化**:結果が複数ある場合(三振・四球・死球・本塁打・インプレーなど)、各結果の倍率を掛けた後、確率の合計が1になるよう調整(正規化)する必要がある。
- **打席結果の第2段階の残りの詳細**:担当ポジションまで決めること(D-038)は決定済み。残りの検討点は、打球の種類(ゴロ・ライナー・フライ)ごとの割合、失策の決め方、走者の進塁、長打の扱い。
- **検証の方法**:シーズンを繰り返し回して、リーグ平均の率・得点が一般的な水準に収まるかを確かめ、設定値を校正する。
- **段階1・第1弾の実装の区切り案**:次の順に、1つずつ PR にする(下の段が上の段に依存するため、この順にする)。
  1. 選手の生成
  2. 1回の打席の計算
  3. 1試合の進行
  4. シーズン(日程・順位)
  5. 指標の集計(第1弾の指標)
  6. セーブ・ロード
- **野手が処理できない打球の割合の持ち方**:長打など、野手が処理できない打球(D-038)の割合を、どの設定値として、どう持つか。
